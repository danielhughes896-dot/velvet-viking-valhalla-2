# Race Day out of the training week's total

Branch `claude/race-week-volume`, cut from `main` @ `565a1bc` (the
race-day-hierarchy merge).
**Not merged. Held for founder review.**

---

## 1. The number, before and after

A 13-week marathon block, 45 km/week starting volume, generated by the app's
own `buildBlockWeeks` / `buildDaysFromWeeks`. These are its last four weeks:

| Week | Phase | Before | After |
|---|---|---:|---:|
| 10 | Peak | 0/79 km | 0/79 km |
| 11 | Taper | 0/59 km | 0/59 km |
| 12 | Taper | 0/40 km | 0/40 km |
| **13** | **Race Week** | **0/67.2 km** | **0/25 km** |
| | | *+ "Total includes race day: 25 training + 42.2 race = 67.2 km"* | *RACE DAY · October 18, 2026 · **42.2** km* |

**The taper reversed on its own final week.** 79 → 59 → 40 → **67.2**. The week
in which the athlete is meant to do least read as a bigger week than nine of the
block's twelve genuine training weeks, and the note underneath existed only to explain a
sum that should never have been added in the first place.

## 2. This was not a new opinion

The engine already held this line. `largestScheduledWeek()` — the figure
`progressionJustification()`'s "did the athlete reach the top of the last block"
gate is judged against — has always excluded race days, and its own comment
calls that *"the same split `weekVolume()` already makes for display"*.
`weeklyCompletedTrainingVolumes()` excludes them too.

`weekVolume()` did make the split. It returned `{ total, done, race, training }`
and had done for some time. **The header simply printed `total`.** The whole
defect was one expression in one line of markup, and the fix is the other field
that was already there.

### How it survived a pass aimed straight at it

`test/raceWeekVolumeMethodology.test.js` — the engine-side fix — states in its
own header:

> *"weekVolume() (the Full Plan week-card display) already made exactly this
> training/race split for the same reason; the peak-comparison gate now makes
> it too."*

That sentence was true of the **function** and false of the **screen**, and it
is exactly why the display was left alone by a piece of work that was otherwise
about this precise question. The new tests therefore read the rendered markup,
not the returned object — asserting `weekVolume().training` would have passed
before this change too.

## 3. What changed

### `weekVolume()` — one new field
`training` and `race` already existed. Added `doneTraining`: completed training
excluding the race. Without it, the header would have read **42.2/25** the moment
the race was logged — the same defect, arriving later.

`total` and `done` are **unchanged and still returned**. They are the week's real
kilometres, race included; removing them would be a different and unasked-for
change.

### The week header
```diff
- kmToDisplay(vol.done)  + '/' + kmToDisplay(vol.total)
+ kmToDisplay(vol.doneTraining) + '/' + kmToDisplay(vol.training)
```
Same change in `patchDerivedStats()`, which rewrites that header in place after a
log without a full re-render. Left alone, the race would have silently reappeared
in the header the moment anything was logged — the defect would have come back
only for athletes who actually use the app.

### The combined-total note — deleted
`raceNote` is gone. With the race out of the header there is nothing left to
explain.

### `renderRaceDayEvent()` — Race Day, on its own
The race used to be the seventh day card in a list of seven. It now renders once,
below its week, under its own divider:

```
RACE DAY ─────────────────────
October 18, 2026        42.2 km
┌──────────────────────────────┐
│ Sun Oct 18  RACE DAY  ·KEY   │
│ Full Marathon Race Day       │
└──────────────────────────────┘
```

**Nothing about the session changed.** It is the same `renderDayCard()` on the
same day object — same prescription, same pacing, same logging, same
`sessionImportance()` of `KEY`. Only where it sits and how it is introduced are
different, and the week accordion no longer lists it, so it appears exactly once.

The label comes from `vGoalDay()` — "Race Day" for a real event, "Goal Day" for a
self-set target — so this invents no second vocabulary.

### This Week gets the same treatment
`renderWeekAccordion()` is shared by Full Plan and This Week. Without applying the
split to both, an athlete in race week would have seen the race inside the week on
one screen and standalone on the other, **with two different weekly totals for the
same seven days**.

### One thing the audit turned up: the zone chart
`computeWeekZoneBreakdown()` sits inside the week body, under the day cards, and
counted the race. With the race no longer listed there, race week's chart would
have described 42.2 km of goal-pace running the athlete could not see above it —
for a marathon, **more goal-pace time than the entire rest of the week**, so the
chart read as a 60% marathon-pace block. It now excludes the race for the same
reason and by the same principle. Race week's chart reads **98% easy / 2%
interval**, which is what that week is.

## 5. Tests — `test/raceWeekVolumeDisplay.test.js`, 21 new

Proving, in order:

1. the race week header shows training volume only, not training + race
2. **the taper keeps descending all the way to race week** — and asserts the
   old figure would have broken it, so the fixture cannot pass vacuously
3. the combined-total explanation is gone from the product *and* from the source
4. the race session is still in the programme, with its prescription intact
5. the race day renders **exactly once**, standalone, below the last week
6. every other day of race week is still listed inside the week
7. weeks without a race are completely unaffected — header, totals, all of it
8. `total`/`done` are still available to callers that want them
9. `largestScheduledWeek()` still agrees with the week headers
10. logging the race does not push the header past its own target
11. the completed race is still recorded as a measured performance
12. the race is still kept out of completed weekly training load
13. rendering the plan never mutates the schedule
14. **This Week shows the same split as Full Plan** during race week
15. a non-race week on This Week is unchanged and carries no race event
16. the live stats patch writes the training split, not the all-in total
17. the week accordion filters the race out in one place
18. the weekly zone breakdown describes the sessions the week actually lists
19. non-race weeks' zone breakdown is untouched
20. a half-marathon block splits the same way
21. the standalone event uses the plan's own name for the day

### Mutation-checked, not assumed

Reverting the header to `vol.total` and putting the race back in the week body
fails **6** of them. Removing the zone-chart exclusion fails **1** more. Two of
these assertions read the runtime source with comments stripped first — matching
prose instead of code has produced a false pass in this suite before.

## 7. One existing test updated, not weakened

`test/adjustedSessionStructure.test.js` — *"no surface renders a day card by a
route of its own"* — counted `renderDayCard(` call sites and required exactly
three. The standalone race event is a fourth, so it failed.

What that test protects is **a second presentation of the same session**, and
that is still exactly one apiece: `renderRaceDayEvent()` renders the shared
`renderDayCard()`, and the week accordion filters the race out precisely so the
standalone event is not a duplicate. The count moved to four and two assertions
were **added**, not relaxed:

- the accordion must use the shared card *with the race filtered out*
- the standalone event must render the shared card, not a card of its own

It also now strips comments before counting. `renderRaceDayEvent()`'s own
comment names `renderDayCard()` in order to say that it reuses it, and counting
that as a call site would have failed the test for the one thing it exists to
permit.
